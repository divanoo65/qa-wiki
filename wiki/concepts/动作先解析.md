## 概念定义

动作先解析是 Harness Agent 架构中一项关键的防范机制，旨在解决意图路由后流水线中函数签名与逻辑不匹配的“设计坏味道”。在典型的 Agent 系统中，用户请求经过意图路由（如 `Intent Router Agent`）被分类后，需要由具体的流水线（Pipeline）执行后续操作，例如研究、内容变换、知识图谱构建等。然而，传统实现中容易出现 `parse_intent_actions()` 函数虽然接受 `intent` 参数，但在内部完全不使用它；或者 `build_content()` 等函数的签名中包含 `intent` 但逻辑却忽略该参数，导致实际执行的动作与原始意图脱节。动作先解析机制强制将动作（actions）的解析作为流水线的第一步，要求 `parse_intent_actions()` 在一切处理逻辑之前运行，并将 actions 作为后续所有函数的必传参数。这种设计从根上杜绝了“函数喊了意图却不用”的模糊现象，使得每个处理步骤都清楚自己当前被要求执行的具体动作（如翻译、摘要、格式化等），而不仅仅是抽象的“意图”。同时，该机制与“意图契约”相辅相成：意图契约规定每个处理意图的函数必须声明支持哪些动作，而动作先解析则确保这些声明在运行时被强制执行。通过这种前置检查，系统可以在早期捕获动作与意图不一致的错误，避免在流水线后半段才发现问题。

## 技术细节

动作先解析在 Harness Agent 中的实现依托于流水线（Pipeline）定义（如 `sop.yaml`）和 `spawn` 守卫机制。具体而言：

- **函数签名约束**：所有意图处理函数的签名必须包含 `actions` 参数，且该参数应当被首先解析。`parse_intent_actions()` 作为流水线的 Stage 0 或前置步骤，接收原始意图并返回结构化的动作列表（例如 `["translate", "summary"]`）。后续的 Stage（如内容变换、知识构建）的入口函数必须将 `actions` 作为必传参数，并在逻辑中只处理列表中声明的动作。
- **与意图契约的协同**：每个处理意图的函数（如 `handle_translate`, `handle_summarize`）在注册时通过装饰器或配置文件声明其支持的动作集合。`parse_intent_actions()` 在解析时会进行匹配校验：若用户意图隐含的动作不在当前函数声明的支持范围内，则提前拒绝执行并返回错误，避免无意义的处理。
- **测试验证升级**：传统测试只验证“pipeline 是否触发”，不验证“内容是否符合意图”。引入动作先解析后，测试用例必须包含对 actions 参数的正确传入测试，例如：`输入意图“翻译成中文” → 期望 actions = ["translate"] → 验证输出内容语言为中文`。这迫使测试覆盖到内容验证层面。
- **性能开销优化**：由于动作先解析仅涉及一次轻量级的动作提取与匹配，与后续的 LLM 调用或数据抓取相比开销极小，因此放在流水线最前端完全可行，并且能尽早失败，节省资源。

## 应用场景

- **多动作混排的流水线**：当同一个流水线需要根据用户意图执行不同组合的动作时（例如先“研究”后“内容变换”），动作先解析能确保每个 Stage 只执行其支持的动作子集，避免不匹配。例如在 `sop-content-transform` 中，若用户意图是“总结+格式化为 Markdown”，则 `transform` 会收到 `actions=["summarize","format_markdown"]`，而不会错误地执行其他操作。
- **防止空转和资源浪费**：在大型 Agent 系统中，流水线可能涉及昂贵的 LLM 调用或外部 API 请求。动作先解析在流水线最前端就判断当前动作是否可执行，若不可执行则立即终止，避免后续无意义的计算。
- **多语言/多格式输出管控**：对于“翻译意图 → 验证输出是中文”这类验收标准，动作先解析与内容验证结合使用，有效防止翻译流水线输出非目标语言的情况。
- **接口虚拟化与配置驱动**：在 Harness Agent 的配置驱动架构中，不同的 Pipeline 可以共享相同的 `parse_intent_actions()` 逻辑，而各个 Stage 通过配置文件单独声明支持的动作集合，实现了高度的灵活性和可复用性。动作先解析正是这种解耦的核心纽带。
