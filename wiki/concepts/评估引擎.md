# 评估引擎

## 概念定义

评估引擎（Evaluator）是 Pipeline 架构中专门负责对 Stage 输出内容进行质量检测与打分的组件。它与 Phase Guard 正交：前者检测**进程是否活着**（流程完整性），后者检测**输出内容是否好**（结果质量）。评估引擎不能替代阶段守卫，因为只有守卫确认 Stage 跑完后，评估引擎才有输入可供检查。评估引擎的典型工作方式是结合规则检查与 LLM 打分（例如 Gemini），对生成的结果给出量化评分，从而判断是否需要触发重跑或其他补救措施。

评估引擎的设计核心在于**避免盲目重跑**。若 Stage 的输入与 Prompt 未发生变化，且 LLM 温度较低时，重跑大概率得到高度相似的结果，无法解决评分低的根本问题。因此评估引擎需要与根因分析联动，确定低分的真正根源（如上游数据偏差、Prompt 设计缺陷或 LLM 幻觉），而非简单地触发重跑。评估引擎的引入使得 Pipeline 能够从“是否跑完”的二元判断升级为“跑得好不好”的维度，是实现 Pipeline 可靠性闭环的关键组件。

## 技术细节

- **检测维度**：评估引擎关注输出内容的正确性、完整性、一致性等质量属性。具体评分规则可包括正则匹配、关键词检测、格式校验等硬规则，以及基于 LLM 的语义评分（如事实一致性、逻辑连贯性）。
- **评分阈值**：通常设置一个可配置的阈值（如 0~100 分），低于阈值则触发告警或重跑。阈值需根据实际场景调优，避免过于严格导致无效重跑。
- **与 Guard 协同**：Guard 检测 Stage 是否完成（通过 Git log 中的 done commit 等标志），评估引擎在 Guard 确认完成后才运行。两者形成两层保障：流程保障 + 质量保障。
- **重跑策略**：评估引擎应记录低分的具体原因，为后续的重跑决策提供依据。例如，若为 LLM 随机性导致的波动，可考虑提高温度并重跑；若为 Prompt 问题，则需人工干预。

## 应用场景

- **Wiki 构建 Pipeline**：在多种数据源生成 Wiki 页面的场景中，评估引擎对最终输出的 Wiki Markdown 进行评分，确保内容准确且格式规范。低分可能触发重新生成，但需结合根因分析避免无效重跑。
- **LLM 生成代码审查**：在自动化代码审查系统中，评估引擎对 LLM 生成的代码块进行语法检查、安全漏洞扫描及逻辑正确性评分，辅助开发决策。
- **多阶段生成任务**：如生成报告、摘要、对话回复等 Pipeline，评估引擎可以内嵌在每个 Stage 之后，反馈质量信号以驱动自适应调整（如切换 Prompt 模板或调用不同模型）。
