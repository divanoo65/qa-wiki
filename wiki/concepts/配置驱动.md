# 配置驱动

配置驱动（Configuration-Driven）是 Harness Agent 架构设计的核心原则之一，其本质在于通过外部化配置来定义 Agent 的行为逻辑、执行流程以及环境适配，从而实现智能决策层（Brain）与执行层（Hands）之间的完全解耦。在传统 Agent 系统中，任务编排、技能调用、参数传递往往硬编码在代码中，导致扩展性差、维护成本高、环境切换困难。Harness 引入配置驱动机制后，Agent 的每个 Skill（原子工作流节点）及其编排顺序均由独立的配置项决定，Brain 仅通过标准化接口（如 `read()`、`write()` 之类抽象命令）下发意图，无需关心底层执行环境是本地沙盒、远程容器还是物理设备。这种设计借鉴了操作系统对硬件的虚拟化思想：操作系统对磁盘、内存、外设进行抽象，上层应用通过系统调用访问统一资源；Harness 则对执行环境进行虚拟化，通过配置描述每个 Skill 的输入输出格式、执行条件、失败重试策略、超时阈值等属性，使得同一套 Brain 逻辑可以在不同场景下复用不同的 Skill 实现。

从技术细节来看，配置驱动的实现依赖于一套结构化的配置模型。该模型通常包含以下几个层次：第一层是 **Skill 定义配置**，描述每个原子节点所封装的具体逻辑、依赖的外部服务、预期的输入输出 schema；第二层是 **编排配置**，以 DAG 或顺序列表的形式定义 Skill 之间的依赖关系与执行顺序，并在关键节点注入条件分支判断——但条件分支本身不在 Skill 内部实现，而是由 Brain 根据上下文动态选择下游 Skill；第三层是 **环境配置**，指定每个 Skill 运行所需的基础设施（如计算资源、网络策略、安全凭据），并允许通过环境变量或配置中心动态替换。此外，配置驱动还支持 **动作先解析** 机制：在正式执行前，Agent 先加载配置并验证所有依赖项的可用性，确保配置合法性，若配置不符合预期则立即告警而非运行时崩溃。这种设计极大提升了系统的可靠性与可审计性。

在应用场景中，配置驱动广泛覆盖了 Harness Agent 的各个组成部分。例如，在 **流水线**（[[流水线]]）中，用户无需修改任何代码，仅需通过 YAML 或 JSON 配置文件定义阶段、任务、并行分支，即可生成一条完整的 CI/CD 流水线；Brain 根据当前上下文选择匹配的流水线配置，并顺序触发各个 Skill。又如，在 **内容验证** 场景中，配置驱动允许运维人员为不同环境（开发、测试、生产）分别定义验证规则集（如安全扫描阈值、性能基准线），Agent 在执行验证时自动加载对应配置，无需为每个环境重复部署相同的逻辑。再如，在 [[接口虚拟化]]（[[接口虚拟化]]）中，配置驱动使得 Brain 可以调用同一个标准化接口（如 `execute`）而无需关心底层是本地命令执行、远程 SSH 调用还是 Kubernetes Pod 创建，接口的具体实现由配置中的“适配器”字段决定。这种机制让 Harness Agent 能够在多云、混合云环境中无缝迁移，真正实现“一次编排，到处运行”。
