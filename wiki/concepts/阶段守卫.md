# 阶段守卫

## 概念定义

阶段守卫（Stage Guard）是流水线（Pipeline）可靠性设计中的核心守护机制，部署于每个 Stage 之后，专门负责检测该阶段进程是否正常执行完毕。与通常意义上的质量评估不同，阶段守卫不关心输出内容的“好坏”，而是聚焦于流程的“完整性”——它回答一个二元问题：这个 Stage 有没有跑完？在具体实现中，阶段守卫通过读取 Git 历史中是否存在该 Stage 产生的 done commit 来进行判断。一旦确认 done commit 存在，则证明进程完整走完且没有中途崩溃、死锁或超时；若未发现，则触发重跑或告警。阶段守卫的存在使得后续的评估引擎（如 wiki-evaluate）能够获得可靠的输入——只有确信 Stage 已经完成，评估器才具备对输出内容进行质量打分的条件。因此，阶段守卫与评估引擎构成正交关系：一个保障流程可靠，一个保障结果可靠，两者缺一不可。这种设计避免了因进程异常导致评估器面对空输出或残缺数据而误判的情况，大幅提升了 Pipeline 的整体稳定性。

## 技术细节

- **检测对象**：进程是否活着（alive），而非输出质量。
- **判断方式**：查看对应 Stage 完成后是否向 Git 仓库提交了一个特定格式的 done commit（例如 commit message 包含 `[stage-guard] stage_name:done` 标记）。
- **健康契约**：每个 Stage 在启动时需注册自身的 done commit 模板，阶段守卫通过 `git log --oneline --grep` 定期检查。若超时未发现匹配 commit，则认为故障。
- **触发动作**：一旦守卫判定 Stage 未完成，可执行重跑（re-run）该 Stage、回滚到前一阶段、或向监控系统发送告警。注意：重跑由守卫触发，与评估引擎的评分低重跑是两套不同逻辑，前者解决流程断裂，后者解决质量不足。
- **与评估引擎的关系**：阶段守卫是评估引擎的前置条件。评估引擎只有在守卫确认完成之后才启动，否则评估没有意义。

## 应用场景

1. **SOP 多阶段构建管道**：例如在“数据清洗→特征工程→模型训练→模型评估”的 Pipeline 中，每个阶段后面都需部署一个阶段守卫，确保上游产出物完整无误地交付给下游。
2. **LLM 工作流中的长链条任务**：当使用 [[Reflection Agent]] 进行多轮自我改进时，每个自我反思步骤可视为一个 Stage，阶段守卫确保每轮反思的调用结果（如是否有输出异常截断）被记录，避免无效递归。
3. **自动化 CI/CD 流水线**：在代码构建、测试、部署各环节加入阶段守卫，防止因脚本非正常退出导致发布流程中断，与 [[评估引擎]] 配合形成完整可靠性体系。
